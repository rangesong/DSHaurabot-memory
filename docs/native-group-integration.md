# 0.6.0 原生群聊注入协作

本次在0.6.0群聊生命周期上补齐Aurabot原生memory和history-vault的准备阶段适配。三条路径读取同一份W5群聊开关及1/2/3/4天期限，不按正文是否出现“群”判断来源。

## 原生memory

实际宿主原先运行的是内置memory，modules/memory中有一份未启用的旧副本。部署从当前内置源码、使用宿主自身的导入改写器生成用户副本，保留当前存储接口与其它能力，再添加带哈希验证的补丁；切换memory的useBuiltin，不替换Aurabot整包源码。更换宿主版本后，补丁基线不符会停止，不能盲目覆盖。

过滤位于索引建立及检索之前，涵盖词法、向量候选及关联；异步重排后按当前原始条目再次检查。尾部原文、主人私聊中的跨会话群聊补充和群聊背景也逐条进入策略。私聊和自身经历继承原行为。原生工具可明确查尚未转移的冷资料，但已移入废弃库的对应来源不会通过工具复活。

原生画像整理、流水提炼与反思、细节压缩、合并和联想建边的内容入口也执行相同策略，内部调用不因没有传入聊天参数而绕过过滤。残迹可用于召回，但不再用残迹背后的完整旧原文重新提炼画像或长期印象。准备阶段不改原生有效期、不删源记录，主人的私聊原有整理继续保留。

原生永久/核心、重要档位、较高重要度、未完成跟进及Thinkstar仍需保护的规范来源保留。没有原始依据的旧画像、相处经验及旧gist不能安全拆分，记录为保守暂留；不把未知当普通，也不靠全文关键词抹除用户正文。接入状态使用covered_with_conservative_holds，不能解释为所有遗留摘要均已完成来源对齐。

## history-vault

自动备忘中可能混合过期闲聊与重要约定。因此群聊备忘不再直接使用未经拆分的旧日摘要，而从对应L0原文逐条筛选、本地重建可用导航。两天残迹注明不是完整原话；到期普通内容不进入新备忘，不增加模型调用。原始L0、L1和L2不在此适配中删除。

已转移来源通过稳定指纹拦截，普通历史工具也不展开包含退休来源的旧摘要；需要时在数量限制内提供尚可用的原文。主人私聊的原有备忘和分层读取保持不变。已有会话里的历史文字不自动改写，不能把过滤未来注入说成已删除所有旧上下文。

## 旧记录整理与后续运行

管理员入口group-cleanup要求明确的before时间，按真实消息时间、仅群聊、分页导入及有限批次应用，进度可恢复。原生重要档位先落实保护，再进行治理。与当前人格原文准确对应的vault记录复用已有来源；无法对应的共享原文保存在独立的“历史原文·未归属人格”命名空间，不作为当前人格的学习经历。

本次用户授权立即处理北京时间2026-11-19零点之前的群聊来源。已符合阶段的直接完成本地残迹或到期转移，不修改消息时间、不提前淘汰未到期内容。P0/P1、必要原证据、未完成事项、待交接及无法安全判断的内容继续保护。

后续仍按原有夜间维护窗口运行，原生来源分页和治理各有界处理，不在白天自动集中补跑。新增来源携带稳定关联标记；转移后副本只在rubbishmemory年月库保存，日常流程只核对主库的退休标记，不读取废弃副本、不学习或自动恢复它。明确隐私删除及手动恢复沿用既有机制。

## 部署、确认与回退

Thinkstar通过scripts/update-aurabot-module.js更新；原生适配通过scripts/update-native-group-adapters.js更新。均先将明确清单内的旧代码上传GitHub Releases，经公开下载、逐文件落盘恢复及哈希校验后再替换。数据库、聊天、配置、垃圾桶和私人模型不上传。正式整理前另留本机SQLite在线恢复点。

先执行受管合成回归及代码包检查，再部署两部分。真实宿主通过native-policy-status检查配套接线，通过native-policy-probe在原生helper中验证合成的到期/保护/私聊条目；不创建测试记忆、不调用模型、不发QQ。接线不全或验证失败时停止历史整理，先修复再验证。

数据库schema仍为2，新增内容为已有对象属性和元数据。代码回退不自动恢复已转移记忆；普通恢复用垃圾桶，整批回退需核对本机恢复点与之后的新记忆。原生memory仍是同一个模块ID与业务库，鱼的世界等其它模块的调用保持原接口。

详细部署回执、真实整理数量和保护/暂留数量另见本次本机运行报告；合成回归不是多年自然运行或最终QQ回复质量的证明。
