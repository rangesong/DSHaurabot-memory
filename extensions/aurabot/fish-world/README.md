# Fish world life module

Canonical source: extensions/aurabot/fish-world. Node built-ins only, no new database or model assets. Requires compatible Aurabot module API with tools guards, session/event, llm/stream, Agent.whenIdle, sessionQuery and core/usage.js. Existing persona, MCP, QQ, keys, quotas, sharing and non-blocking prompt refresh remain in place.

## Purpose continuity

Known business-rule rejections remain available across rounds, incremental snapshots and existing window rotation. A pure bounded projection reads only attributable owned-world journal results and returns at most four conditions within 2400 serialized characters. It keeps the failed business arguments, original time and receipt reference; transport request IDs are omitted. Only a confirmed success of the same business action removes that rejection. Stock quantities, navigation, model notes and later unrelated actions cannot silently erase it. Later mutation references are facts to inspect, never automatic proof that a condition was repaired. Closed unrelated purposes and old unlinked failures stay out of idle context. This adds no execution guard, automatic retry, wakeup, share or model call.

Plans retain their original goal when their next stage is refined. A progress update without successful receipt references is retained as an explicitly model-reported note instead of being silently discarded; it does not prove progress, complete a task or release an unknown outcome. Existing and receipt-linked progress text is labelled as a note as well. Real action attribution remains the source of progress, and navigation carries an explicit partial-stage label while preserving its original arguments and replay protection. Original goals, progress notes and known rejections use the existing bounded handoff; the window algorithm, quotas and time/call budgets are unchanged. New note fields are additive within runtime 3/life 2; keep the latest ledger when restoring older code.

The full-ID evidence rule retains one narrow declared-protocol compatibility path: a fresh current home observation may declare `throw-` plus an owned food item ID, with that exact inventory item explicitly marked spoiled. Both the action wrapper and intent validator use the same proof over the original template and inventory lines, quantity, round/session, and unchanged observation. Merely aging food, another item, quoted text, stale observations, later mutations and guessed recipe IDs do not qualify. This never constructs a fake server receipt or dispatches an automatic cleanup; normal identity, budget, guards, registry execution, request IDs and result accounting still apply.

The fixed Asia/Shanghai date formatter is reused during local cost summaries; day boundaries and quota keys are unchanged. Important-experience writes remain pending when the memory service explicitly returns `ok:false`, an error, `isError`, or a debug-only no-write result. Normal native insert/update and Thinkstar ingest receipts remain accepted. Existing five-minute pending-memory retries apply; no model or network probe is added, and prior recorded history is not reclassified.

## Scheduling and plans

Every start, including owner arrangements, recovery, work inspection and plan continuation, uses one durable admission/reservation path. normalMinGapMs=180000; urgentMinGapMs=30000; urgentMaxRoundsPer10Min=4; planRecheckMinMs=600000; unchangedPlanRoundLimit=1. Only trusted work/doorbell/health event versions qualify for an urgent exception. This still consumes the existing daily category quota. Ordinary idle observation is 30 minutes; work fallback, same-plan recheck and same-sender social cooldown are ten minutes. Existing queued messages also honor the current peer cooldown. A wording revision does not bypass the plan interval. Unknown submission reservations are retained, never refunded into retries.

Consecutive incomplete or failed rounds back off for 5, 15, 30, then 60 minutes; further failures remain at 60 minutes. The failure streak and deadline persist across module restarts. Only a valid completed round with real observation and a complete finish report resets the streak. A duplicate end callback is a no-op. The existing explicit owner probe may override the current wait once, but does not erase the streak, quotas, unknown actions or submission reservations. No extra model health probes are made. Read-only recovery can still open a fresh bounded window after the wait and confirmed old-agent stop; a new window is not evidence of a successful recovery.

planChanges supports create/update/complete/expire/abandon/block/supersede/merge. Updates require stable id and expectedRevision; merges/supersedes require targetId and targetExpectedRevision. The program verifies identity, subject, topic, stage, business time window and owner instruction revision. Legacy plans is normalized; repeated create returns the existing ID without reviving waiting/review/terminal state. nextAt is earliest continuation, not expiry. Explicit expiresAt or successful evidence supports terminal disposition. One unchanged check waits for a relevant event, state or explicit future time. Historical ambiguity requires review, never one model call per old row. Clear paraphrases with the same actor, targets, resource, stage and business window refine the existing ID. refinesPlanId supports explicit refinements. Entire added steps and restrictions are retained; deadlines can tighten but cannot silently loosen. Missing-topic or multiple-match submissions become local blocked planProposals, not new scheduled plans or paid recovery rounds.

idleWorkHours and activityWorkHours use Beijing time ranges, including midnight crossings, e.g. 18:00-09:00,12:00-14:00. Empty preserves existing schedules; invalid nonempty input holds starts. Owner and recovery still pass quota, spacing and volume checks. Queues remain intact when paused or exhausted. Quota alerts merge by identity/date/category/reason and are panel notices, never urgent QQ or a sharing backlog.

QQ sharing delivers normal world-life messages only. System fault, timeout and recovery diagnostics stay in the local ledger and module status; enabling sharing never replays historical fault alerts. Read-only recovery-round reports cannot enter the QQ sending path, even when the model supplies a share. Unsent legacy fault notices and recovery notices linked to their original journal rounds are suppressed without deleting their original text or receipts. Existing queued deliveries are only reconciled against their original delivery IDs, and uncertain deliveries are never resent. Important and urgent normal world-life results keep their existing delivery rules. Version 1.3.6 adds only optional local-delivery audit fields within runtime schema 3/life schema 2, changes no database and requires no private-ledger migration; rolling back to an older version can restore its former fault-notification behavior.

Version 1.3.7 makes normal sharing live-only. Results produced while sharing is off stay local; turning it on never flushes an old backlog. The first policy initialization and effective sharing-state transitions archive only unsubmitted pending/deferred/failed messages, preserving their text, original state, attempts and receipts. An optional persistent life.sharingPolicy keeps the observed effective state across module reloads, so an unchanged enabled setting does not discard new pending results. A real change to the settings-page sharing value supersedes an earlier sharing control; a later explicit control takes precedence until the settings value actually changes again. Saving the same settings value or reloading does not undo that control. Unsubmitted shares expire 30 minutes after their original creation time; retries and quiet-hour or quota deferrals do not extend freshness. Missing or invalid original times are not treated as new. Already queued items only reconcile their existing delivery IDs; failed/deferred results from that lookup remain local and are never resubmitted. Uncertain items are never resent. Runtime schema 3/life schema 2 and host settings remain unchanged; rolling back code restores the older sharing policy.

## Context and usage

Version 1.3.18 adds the synchronous `use('fish-world').outreachSnapshot({recipient, persona})` for correcting an existing owner-directed outreach narrative. It returns schema 1 with `available`, current `{owner, persona, fish}` scope, `sampledAt`, `sharingEnabled`, `correctionOnly:true`, `recentIsComplete:false`, bounded current state and at most eight confirmed notification/action references. The complete serialized packet is at most 2000 characters. Only the current owner recipient and persona may read it; live verified world identity and the current credential hash must match. Disabled, migrating, closed or changed identities return an unavailable empty view. It reads the module-owned credential file and cached memory only: no refresh, world/model call, runtime write, full ledger snapshot, new tool permission, schema migration or change to ordinary-chat context is added.

Current fields retain the original observation time and a three-minute freshness limit; later confirmed, executing or uncertain world changes make that sample unknown until normal collection catches up. Server activity clock strings remain unchanged and do not prove completion. Recent facts carry both occurrence and observation times; message notifications prove only that a message arrived, not its unseen contents. Omitted evidence never proves there was no reply. Disabling either body or location auto-injection also omits free-form recent text, which might contain those hidden fields. `sharingEnabled:false` still permits correction of an old false premise but does not authorize proactive world reporting; this interface never supplies new event topics, consumes sharing claims or changes existing sharing, quota, plan or delivery state. Consumers must preserve these limits and recheck the scope before delivery. Code rollback removes only this optional export; latest private data and receipts remain compatible.

Version 1.3.17 resolves an existing bound session through the official host controller before request admission. A missing resident Agent is not an empty conversation. The preflight uses the available registry and persisted request-header tools, keeps the latest complete request estimate for that same owned session as a conservative floor, and reserves 12000 estimated tokens for the following assistant/tool steps. A safe volume-triggered window drops the old history/floor and recalculates its current prompt/tools/reserves. An unavailable old measurement cannot silently reuse the old window. First-ever bootstrap uses an explicit conservative tool reserve rather than treating an empty registry as a one-token schema. The existing 64000 final request guard, 16-round setting, safe-boundary checks, original history and unknown-action protection remain in force; an arbitrarily large later result can still hit the final guard.

Version 1.3.16 adds independently scoped fish-person archives and the local read-only `fish_person_impression` tool. Confirmed peer conversation/profile/friend receipts build a source-backed index, with original times and roles. Re-reading history does not make new events or shares. A completed normal round may supply at most two evidence-backed `peerImpressions` without opening an extra model/world round. Unknown speakers, action-only metadata and public appearance alone cannot license a personality. `people.json` and separately verified `people-identity.json` stay private in module data; native QQ profiles are untouched. The host person wall source switch uses the companion exact-version panel patch. Full instructions and rollback boundaries are in the repository's `docs/fish-world-people.md`.

backgroundContextEnabled retains its current setting; backgroundContextRounds defaults to 16 completed life rounds. A current task carries at most 12 related plans and eight events. Changed records use keyed added/updated/removed. Full plans, source receipts, unknown operations and original sessions remain durable. fish_life_history pages at most ten records and about 4000 characters; part retrieves every byte of long evidence without a model summary.

roundPromptEstimatedTokenLimit=12000; visibleContextEstimatedTokenLimit=48000; requestAdmissionEstimatedTokenLimit=64000. All visible blocks/tools and unknown wrapper reserve contribute to startup estimates; the official final llm/stream hook checks complete request messages/tools/system before forwarding. These are heuristics, not provider tokenizer guarantees. Stopped recovery may use a bounded read-only fresh window after Agent.whenIdle and no tools/outbound execution. It cannot repeat unknown actions. Unbound windows are reused after failed admission. Either visible-history or total projected-request volume can request a safe fresh window; total size cannot permanently stall below the visible threshold. Refinement archives and old migration snapshots remain behind paged history references.

session/event append assistant/message and failed assistant/attempt records are deduplicated by session ID and event sequence. Provider usage and host core/usage.js CNY pricing produce fresh/cached/output and estimatedCny. Missing/late usage is pending then unknown; unknown prices/cache-write pricing are unknown, never free. Records retain round/window/trigger/category/source/plan/reason. Cold-window requests count too. Historical pre-upgrade day usage is unknown until an explicit verified baseline is imported.

costGuardEnabled defaults false (observation only). costSoftLimitCny=2 and costStopLimitCny=3 are configurable startup thresholds. If enabled, unknown/in-flight usage holds new starts; soft threshold holds ordinary idle exploration; stop threshold holds all new automatic rounds. Existing requests may still cost money. No strict per-step or daily bill cap is promised. The panel shows estimates, remaining rounds, blockers and next allowed time; diagnosis expands exact attribution.

## Ordered actions and owner-reviewed maintenance

fish_life_action is offered only on the verified native executor. It uses formal tools.execute without a nested surface log: real guards/results and the durable module journal retain child receipts, while a program-action-sequence record links the real parent seq/turn/step/callId. Missing steps run now, exact self profile, intent, then the approved action arguments. Existing successful prerequisites are reused within that round. Each distinct action has its own intent and program request_id; model request ID or evidence changes cannot replay the same business action. Explicit local guard rejection is not a submitted world action. Unknown results stop and remain read-only recovery work. PTC retains the explicit guarded four-step path. No foreign chat is intercepted.

Life tools render their full structured result explicitly through Aurabot defineTool. The model receives exact receipt IDs, facts, approved arguments and prepared plan IDs; Aurabot's default message-only renderer would otherwise hide these behind a check mark. Invalid finish facts return the current successful receipt ID/tool pairs without accepting rewritten evidence or replaying actions. Installed SDK regression uses DSH_ASAR and AURABOT_SOURCE; it makes no model, world or QQ requests.

scripts/review-fish-world-ledger.js --help describes private owner maintenance. It requires paused fish-world autonomy, an immutable hashed review input, owned raw source sessions, current record hashes/revisions, and verified original evidence. Preparation never changes the live ledger or settings. Apply preserves the fresh original ledger, proposal and receipt in maintenance-backups/maintenance-receipts, patches only the four fish-world timing settings, then commits the reviewed ledger atomically. Interrupted applications are safely retried by operation ID. Original rows and evidence stay intact; superseded composite stages retain their own outcomes and one shared undated peer-event promise. Unproven history remains one local review batch with no model wakeup. No schema number changes in 1.3.1: runtime 3/life 2 gains additive audit fields.

Full host validation must separately show a post-midnight day ledger, real work, idle observation/plan continuation, and actual timeout recovery. Synthetic tests and social samples do not prove these branches. Observe natural events only; never manufacture model calls, expired actions, QQ sends or timeouts for acceptance.

## Owner task continuation

The independent owner-tasks.mjs keeps a durable original instruction, current step, remaining steps, destination, revision and actual receipt references. Current trusted owner prompts capture ordinary world instructions; unscoped generic instructions are activated only by that owner's actual world mutation, so ordinary report/file requests cannot start world rounds. Quotes, examples and questions never create tasks. No historical chat is replayed on installation. Optional “when free” requests wait for idle time and cannot interrupt an existing task. New explicit owner input can renew a known blocked task; unknown outcomes cannot be renewed into an automatic replay.

fish_life_task defines up to eight ordered steps with tool, JSON arguments and nextStep. A go step waits for its exact trusted arrival or a fresh matching destination state; work waits for a real settlement. An activity may request waitFor=done; eventText is optional when a confirmed finite main-activity receipt can bind the exact activity label. A generic receipt step completes only after its matching successful action. Purchase-then-return keeps both steps; movement alone never completes an unperformed action. Program request IDs do not change business identity. Completed steps and unknown submissions cannot be replaced or repeated. The original instruction stays immutable as later steps are refined. History is available through fish_life_history(kind="tasks").

After arrival the owner task takes precedence over incidental life plans. Existing daily quotas, 10-minute work/plan/social intervals and 30-minute idle observation remain in force. The owner conversation must finish before a background continuation starts. A no-progress round stays visibly waiting for evidence rather than treating unrelated eating or shopping as progress. Full task data stays in the private ledger; bounded handoffs preserve the active purpose and next steps across fresh windows/restarts. Private-chat recent-round context uses summaries and history references instead of repeating nested action journals. Exact world_do/world_say aliases normalize only to the existing fish-world MCP names and still run all guards.
